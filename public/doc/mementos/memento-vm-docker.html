Matériel

La VM simule une machine entière ; le conteneur isole des processus qui partagent le noyau de l’hôte.

Que choisir ?

  • Essayer un autre système, garder un poste propre → VM.
  • Laboratoire de sécurité, programme douteux → VM isolée, instantané, réseau coupé.
  • Faire tourner une application identique partout → conteneur.
  • Application + base de données + cache → Docker Compose.
  • Outils Linux sous Windows au quotidien → WSL 2.
  • Les deux se combinent : Docker dans une VM Linux est courant.

Se procurer ISO et images

  • ISO : site officiel du système, empreinte vérifiée.
  • Docker Hub : badges Docker Official Image et Verified Publisher ; regarder la date de mise à jour et le Dockerfile.
  • ! VM « toutes prêtes » (OVA) et images d’inconnus : porte dérobée ou mineur de cryptomonnaie possibles.
  • docker pull n’exécute rien ; docker run, si.

Les hyperviseurs

Type 1sur le matériel, sans système hôteHyper-V, VMware ESXi, Xen, Proxmox VE (KVM)
Type 2application d’un système hôteVirtualBox, VMware Workstation, Parallels

Moteurs de conteneurs : Docker, Podman (sans démon), containerd ; orchestration à grande échelle : Kubernetes.

Règles d’or

  1. Un instantané avant toute expérience.
  2. Un instantané n’est pas une sauvegarde.
  3. Un conteneur est jetable : les données vont dans un volume.
  4. Fixer les versions : postgres:17, pas postgres:latest.
  5. Images officielles ou d’éditeurs vérifiés.
  6. Jamais de secret dans une image.

Sous Windows 11 Famille

  • VirtualBox : fonctionne (hyperviseur de type 2).
  • WSL 2 : disponible — un vrai noyau Linux dans une VM légère.
  • Hyper-V (gestionnaire) et Bac à sable Windows : réservés aux éditions Pro, Entreprise, Éducation.
  • Docker Desktop : les prérequis publiés citent Windows 11 Pro, Entreprise ou Éducation 23H2 ; une note y évoque les éditions Famille, limitées aux conteneurs Linux → à vérifier avant d’installer.
  • Solution sûre : Docker Engine dans une VM Linux.
  • ! Si WSL 2 est actif, VirtualBox passe par la plateforme de l’hyperviseur Windows : plus lent, parfois instable.

La virtualisation est-elle active ?

WindowsGestionnaire des tâches → Performances → Processeur → « Virtualisation : Activé »
Linuxgrep -Ec '(vmx|svm)' /proc/cpuinfo : résultat > 0 = processeur compatible
lsmod | grep kvm : module KVM chargé ?
Ubuntukvm-ok : diagnostic complet (paquet cpu-checker)

Désactivée ? Réglages UEFI (BIOS) au démarrage : Intel VT-x (« Virtualization Technology ») ou AMD-V (« SVM Mode »).

Processeur : PC ou ARM ?

  • VM et images visent une architecture : amd64 (x86-64, PC courants) ou arm64 (Mac à puce Apple, Raspberry Pi, certains portables).
  • Images multi-architectures : Docker choisit seul la bonne variante.
  • Architecture étrangère : émulation possible (QEMU), mais lente.
  • Connaître la sienne : uname -m (Linux) · $env:PROCESSOR_ARCHITECTURE (PowerShell).

Redirection NAT : port hôte 2222 → port invité 22, puis ssh -p 2222 utilisateur@127.0.0.1. ! En mode pont, la VM est exposée au réseau local comme un vrai poste : la mettre à jour.

Créer une VM : les étapes

  1. Télécharger l’image ISO sur le site officiel du système.
  2. Vérifier son empreinte : Get-FileHash f.iso (PowerShell) ou sha256sum f.iso, à comparer à celle publiée.
  3. Nouvelle machine : nom, type et version du système (64 bits).
  4. Mémoire vive, processeurs, disque virtuel (voir ci-dessous).
  5. Insérer l’ISO dans le lecteur optique virtuel, démarrer, installer.
  6. Mettre à jour l’invité, installer les additions invité.
  7. Éteindre proprement, prendre un instantané « propre ».

Dimensionner

MémoireLinux sans bureau : 1 à 2 Go · avec bureau : 4 Go · Windows 11 : 4 Go minimum ; laisser au moins la moitié à l’hôte
Processeurs2 suffisent souvent ; ne jamais dépasser le nombre de cœurs physiques
Disqueallocation dynamique ; 25 Go pour un Linux de bureau, 64 Go minimum pour Windows 11
Windows 11exige aussi TPM 2.0 et démarrage sécurisé (virtuels depuis VirtualBox 7)
Affichagemémoire vidéo au maximum si l’interface graphique rame

États et arrêt

Arrêt ACPIdemande polie : l’invité s’éteint proprement
Extinction forcée= débrancher la prise : risque de corruption
Enregistrer l’étatmet la VM en sommeil sur disque ; reprise à l’identique
Pausegèle la VM en mémoire

Additions invité et intégration

  • Apportent : écran redimensionnable, presse-papiers partagé, glisser-déposer, dossiers partagés, pilotes plus rapides.
  • VirtualBox : menu Périphériques → Insérer l’image CD des Additions invité ; sous Linux, installer d’abord les outils de compilation et les en-têtes du noyau.
  • Dossier partagé sous Linux : /media/sf_nom, accessible au groupe vboxsf : sudo usermod -aG vboxsf $USER, puis rouvrir la session.
  • Équivalents : open-vm-tools (VMware), qemu-guest-agent et spice-vdagent (KVM).
  • ! Presse-papiers, glisser-déposer et dossiers partagés percent l’isolement : les couper pour un laboratoire.

Échanger des fichiers avec la VM

  • Dossier partagé (additions invité) : le plus simple.
  • SSH par la redirection NAT : scp -P 2222 f utilisateur@127.0.0.1: (serveur SSH à installer dans l’invité : sudo apt install openssh-server).
  • Glisser-déposer, presse-papiers : pratiques au quotidien.
  • Clé USB attachée à la VM (menu Périphériques → USB) ou image ISO de fichiers.

VDIformat natif de VirtualBox
VMDKVMware ; lu aussi par VirtualBox et QEMU

qcow2QEMU / KVM : dynamique, instantanés internes

Convertir : qemu-img convert -f vmdk -O qcow2 a.vmdk b.qcow2. Agrandir le disque ne suffit pas : étendre ensuite la partition dans l’invité.

Instantané, clone, export, sauvegarde

Instantanéfige disque (et mémoire si la VM tourne) ; retour en quelques secondes ; dépend du disque d’origine
Clone completcopie indépendante de la VM
Clone liépartage le disque du parent : léger, mais inutilisable sans lui
Export OVAun seul fichier pour déplacer la VM vers un autre poste ou hyperviseur
Sauvegardecopie du dossier de la VM éteinte sur un autre support

! Un instantané n’est pas une sauvegarde : si le disque d’origine est perdu, l’instantané l’est aussi. Supprimer un instantané fusionne les différences sans toucher à l’état actuel. Éviter les longues chaînes.

Monter un laboratoire

  • Deux VM ou plus en réseau interne nommé (ex. labo) : elles se voient, et rien d’autre.
  • Pas de DHCP en réseau interne : adresses fixes (ex. 10.10.10.1, 10.10.10.2).
  • Besoin d’Internet pour installer ? Ajouter temporairement une 2e carte en NAT, puis la retirer.
  • ! Une machine volontairement vulnérable ne va jamais en mode pont.

Fichiers d’une VM (VirtualBox)

VirtualBox VMs/dans le dossier personnel ; un sous-dossier par VM
vm.vbox · vm.vdiréglages (XML) · disque virtuel
Snapshots/disques différentiels, états mémoire
Logs/VBox.logà lire quand la VM refuse de démarrer

! Déplacer, renommer : par VirtualBox, jamais à la main.

Une VM qui rame ?

  • Virtualisation matérielle activée (page 1) et additions invité installées.
  • Disque virtuel sur un SSD ; hôte pas à court de mémoire.
  • Ne pas surallouer : trop de processeurs ou de mémoire ralentit l’hôte… et la VM.
  • Invité Linux : carte réseau paravirtualisée (virtio-net).

Comment Docker fonctionne

Clientdocker …votre terminal
API→
Démon dockerdconstruit, lance, surveilleimages · conteneurs · volumes · réseaux
pull⇄push
RegistreDocker HubGHCR, registre privé…
  • docker build : Dockerfile → image · docker pull : registre → image locale · docker run : image → conteneur.
  • Image = modèle en lecture seule ; conteneur = image + une couche inscriptible, effacée avec lui.
  • Sous le démon : containerd gère les conteneurs, runc les crée à l’aide du noyau (espaces de noms, cgroups).
  • Docker Desktop (Windows, macOS) = démon dans une VM Linux + interface graphique.

Les briques d’un conteneur Linux

Espaces de nomsce que le processus voit : ses processus, son réseau, ses montages, son nom d’hôte
Groupes de contrôlece qu’il peut consommer : mémoire, processeur, disque, nombre de processus (cgroups)
Capacitésles pouvoirs de root découpés ; Docker n’en laisse qu’une partie
seccomp, AppArmor, SELinuxfiltrent les appels système et les accès
Couches (OverlayFS)image en lecture seule, partagée + couche inscriptible propre au conteneur

Aucune « machine » : un conteneur est un processus ordinaire de l’hôte, simplement cloisonné.

Cycle de vie d’un conteneur

imagecreate→crééstart→en marchestop→arrêtérm→supprimé
docker run= create + start

Un conteneur vit tant que son processus principal vit : si ce processus se termine, le conteneur s’arrête.

Nom complet d’une image

docker.io/registre
library/espace de noms
postgresdépôt

  • Registre par défaut : Docker Hub · espace library = images officielles.

Tester la santé d’un service

CMD, ENTRYPOINT et leurs formes

CMD ["app", "-v"]forme exec (JSON) : le programme est le processus 1 et reçoit les signaux → à préférer
CMD app -vforme shell : lancé par /bin/sh -c ; ! docker stop attend souvent les 10 s
ENTRYPOINT + CMDENTRYPOINT ["ping"] + CMD ["localhost"] ; docker run img exemple.org remplace seulement CMD

Couches et cache

  • Chaque instruction produit une couche ; si l’une change, toutes les suivantes sont reconstruites.
  • Ordre : ce qui change rarement en haut (système, dépendances), le code en bas.
  • Installer et nettoyer dans la même couche, sinon les fichiers supprimés pèsent encore :
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

Construction en plusieurs étapes

FROM node:22 AS build          # 1. outils complets
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build              # produit /src/dist
FROM nginx:alpine              # 2. image finale légère
COPY --from=build /src/dist /usr/share/nginx/html

L’image finale ne contient que le résultat : ni compilateur, ni sources, ni dépendances de développement.

Syntaxes

  • -v crée silencieusement un dossier d’hôte absent (appartenant à root) ; --mount signale l’erreur.
  • Un volume nommé vide reçoit le contenu du dossier de l’image ; un montage lié le masque.
  • Droits : le conteneur écrit avec son identifiant (UID) ; aligner avec --user.

Sauvegarder et restaurer un volume

Arrêter d’abord le conteneur qui écrit dans le volume. Pour une base de données, préférer son outil d’export (pg_dump, mysqldump).

  • Joindre l’hôte : host.docker.internal (Docker Desktop ; sous Linux : --add-host=host.docker.internal:host-gateway).

Un compose.yaml commenté

services:
  web:                          # nom du service = nom d’hôte
    build: .                    # image construite ici
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      DB_HOST: db               # le service « db »
    env_file: .env              # variables injectées
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:17          # version fixée
    environment:
      POSTGRES_USER: appli
      POSTGRES_DB: appli
      POSTGRES_PASSWORD_FILE: /run/secrets/db_mdp
    secrets: [db_mdp]
    volumes:
      - donnees:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appli"]
      interval: 5s
      retries: 5

volumes:
  donnees:                      # volume nommé

secrets:
  db_mdp:
    file: ./db_mdp.txt          # hors dépôt Git !

Le mot de passe est lu dans un fichier monté en /run/secrets/, pas écrit en clair dans le YAML. ! YAML : indentation par espaces (jamais de tabulation) ; mettre les ports entre guillemets.

Démarrer dans l’ordre

  • depends_on seul garantit l’ordre de lancement, pas que le service soit prêt.
  • Avec condition: service_healthy, Compose attend que le healthcheck du service réussisse.
  • L’application doit tout de même savoir réessayer une connexion perdue.

Mettre à jour l’application

docker compose pull          # nouvelles images
docker compose up -d         # recrée ce qui a changé
docker image prune           # anciennes images
  • Lire les notes de version ; sauvegarder les volumes avant.
  • ! Base de données : changer de version majeure (PostgreSQL 17 → 18) exige une migration des données.
  • Image construite localement : docker compose up -d --build.

Principe

  • Un fichier décrit toute l’application : services, réseaux, volumes, secrets.
  • Nom par défaut : compose.yaml (préféré) ; docker-compose.yml reste lu.
  • Commande actuelle : docker compose (avec une espace) ; l’ancien docker-compose (tiret) est obsolète.
  • La clé version: en tête de fichier est obsolète : Compose l’ignore et avertit.
  • Un réseau projet_default relie les services : chacun joint les autres par son nom.
  • Projet = nom du dossier, préfixe des conteneurs et volumes (-p nom pour le changer).

Mémento — VM & Docker

Durcir un conteneur

--user 1000:1000ne pas tourner en root
--read-only --tmpfs /tmpsystème de fichiers en lecture seule
--cap-drop ALLretirer les privilèges du noyau (--cap-add au cas par cas)
--security-opt no-new-privilegesinterdire l’élévation (setuid)
--memory · --cpus · --pids-limitborner les ressources
-p 127.0.0.1:…ne rien exposer sans raison
--network nonecouper le réseau
  • ! Jamais --privileged ni -v /var/run/docker.sock:… sans comprendre : c’est donner l’hôte.
  • ! Le groupe docker donne des droits équivalents à root sur l’hôte (documentation officielle). Alternatives : mode rootless, Podman.
  • Images officielles ou d’éditeurs vérifiés ; version fixée ; les mettre à jour ; analyser les vulnérabilités (docker scout cves image, Trivy, Grype).
  • Secrets : fichiers montés (secrets:), jamais dans l’image ni dans le dépôt.

Exécuter un programme douteux

  1. VM dédiée, jamais le poste principal ni un conteneur : le noyau partagé rend l’évasion plus plausible.
  2. Instantané propre avant, retour à cet instantané après.
  3. Réseau interne ou non connecté ; pas de dossier partagé, de presse-papiers ni de glisser-déposer.
  4. ! WSL n’est pas une frontière de sécurité : Linux y lit et écrit les fichiers Windows (/mnt/c).
  5. Idéalement : inspection du code avant toute exécution.

Sécurité des VM

  • Mettre à jour l’hyperviseur : des failles d’évasion de VM existent.
  • Un instantané pris VM allumée contient la mémoire : mots de passe, clés… le protéger comme la VM.
  • Données sensibles : chiffrer le disque dans l’invité (LUKS, BitLocker).
  • N’importer que des OVA de source sûre ; couper dossiers partagés, presse-papiers et USB quand ils ne servent pas.

Service en production : liste de contrôle

  1. Image à version fixée, base officielle, reconstruite régulièrement.
  2. Utilisateur non root, privilèges retirés (--cap-drop).
  3. healthcheck et restart: unless-stopped.
  4. Limites de mémoire et de processeur ; journaux bornés (max-size).
  5. Ports liés à 127.0.0.1, derrière un proxy inverse en HTTPS.
  6. Volumes sauvegardés et restauration testée.
  7. Secrets hors de l’image et du dépôt ; mises à jour surveillées.

Docker ↔ Podman

  • Mêmes commandes : podman run, podman ps, podman build… (alias docker=podman).
  • Sans démon et sans root par défaut ; notion de pod (groupe de conteneurs).
  • ! Donner les noms d’images complets : docker.io/library/nginx:alpine.
